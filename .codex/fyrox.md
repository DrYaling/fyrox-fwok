# Fyrox 开发速查
参考文档：https://fyrox-book.github.io/introduction.html
插件实现 `fyrox::plugin::Plugin`，在 `init` 创建 UI，在 `update` 做逐帧逻辑，在 `on_os_event` 处理键盘。`cdylib` crate type 为 Project Manager Hot Reload 保留动态库入口。

## 插件模块化约定

`Plugin` 实现是组合根，不是业务逻辑容器。生命周期方法只负责调用各模块并处理错误：

- `init`：创建场景/UI、初始化运行时和桥接对象；具体构建过程分别放在 `scene`、`interface`、`runtime` 等模块。
- `update`：按固定顺序编排输入、玩法状态、场景同步、UI 命令和脚本事件；每个阶段由独立模块实现。
- `on_ui_message` / `on_os_event`：只做事件过滤和路由，把输入转换成领域命令，不直接修改多个子系统的内部字段。
- `on_deinit`：按所有权顺序释放运行时资源；清理逻辑属于拥有资源的模块。

推荐的职责映射如下，新增能力应放入相同类别的模块而不是扩大入口文件：

| 模块 | 只负责 | 不负责 |
| --- | --- | --- |
| `scene` | 场景/节点创建和句柄布局 | UI、输入、Lua 注册 |
| `interface` | UI 构建、UI 目标和消息提交 | 玩法规则、脚本扫描 |
| `input` | 键盘/鼠标到领域命令的映射 | 直接操作场景或 UI |
| `state`/玩法模块 | 领域状态和规则更新 | Fyrox UI 构建、文件读写 |
| `lua_api`/`bindings` | Lua 可见类型、函数和桥接命令 | 每帧调度、场景装配 |
| `runtime` | Lua VM 生命周期、脚本加载和调度 | 具体游戏玩法 |

`lua-binding/src/lib.rs` 只声明模块并 re-export 公共类型；配置、事件、绑定清单、反射和运行时分别维护在各自文件。新增公开 API 时先确定所属领域，再放入该模块；如果一个 API 同时包含 UI、场景和脚本职责，应拆为多个窄 API，通过 typed command/event 连接。

## Fyrox 边界规则

- UI 图句柄和场景图句柄是不同类型/上下文，禁止用一个“通用节点接口”掩盖差异；失效句柄返回明确错误。
- 不在每帧或每个节点重复注册 Lua 类型；注册发生在运行时初始化阶段，逐帧代码只处理状态同步和事件分发。
- 引擎对象的可变访问集中在拥有它的模块；跨模块只传递值类型、句柄或不可变快照，避免泄漏 Rust 借用。
- 当某个生命周期方法开始包含多个独立阶段，先提取模块函数或协调器，再继续添加功能；不要通过继续堆叠条件分支扩大入口文件。

## 实现自检

1. 为新类型标注所属领域和所有权模块。
2. 检查入口文件是否仍然只做装配/路由。
3. 检查公开 trait 的方法是否服务同一个调用方和能力。
4. 为每个新模块添加最小单元测试；跨模块契约再补集成测试。
5. 使用 `cargo fmt --check`、相关 `cargo test` 和项目脚本验证实际行为。
